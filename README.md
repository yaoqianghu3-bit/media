# 知乎热榜选题面板

每小时抓一次知乎热榜，攒成两个界面，用来决定"今天写什么"。

## 两个界面

**界面 1 · 日级面板**：取最近 **24 次**快照的全部条目，按 `question_id` 去重，每行给出

| 列 | 含义 |
|---|---|
| 热榜话题 | 标题（已按知乎问题 id 去重） |
| 峰值热度 | 这 24 次里达到过的最高热度 |
| 当前热度 | **最近这一次**的热度；最近这次没上榜就是 `-` |
| 本次排名 | 最近这一次的排名；没上榜就是 `-` |

默认**按峰值热度降序**。点击表头可换列排序，点任意一行展开界面 2。

**界面 2 · 话题详情**：该话题近 **3 日**（72 次）的每一次采集记录，时间倒序，含排名Δ、热度Δ、热度变化率、回答Δ、关注Δ、是否新上榜。

## 跑起来

```bash
pip install -r requirements.txt     # 只缺 fastapi 的话可以只装它
python src/main.py
```

打开 <http://127.0.0.1:8000>。启动时会先抓一次，之后每 60 分钟抓一次（进程内定时器，关掉程序就停）。

手动抓一次（调试用，默认受 10 分钟最短间隔保护）：

```bash
curl -X POST "http://127.0.0.1:8000/api/fetch?force=true"
```

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 面板页面 |
| GET | `/api/status` | 采集进度、累计条数 |
| GET | `/api/topics?window=24` | 界面 1 数据 |
| GET | `/api/topics/{question_id}?window=72` | 界面 2 数据 |
| GET | `/api/snapshots?limit=48` | 快照列表（含原始文件路径与体积） |
| GET | `/api/snapshots/{id}/raw` | 下载该次快照的接口原始 JSON（gzip） |
| POST | `/api/fetch?force=false` | 手动触发抓取 |

## 原始留档

每次抓取除了解析入库，还把**接口返回的原始 JSON 原样落盘**（gzip 无损压缩，解压后与响应字节一致）：

```
data/raw/2026-09/20260913-015220.json.gz
                └── 请求时间戳，一个快照一个文件
```

- `snapshot.raw_path` 记录该次快照对应的文件路径，可从 `/api/snapshots` 反查
- 实测 **约 18 KB/次**（gzip 后），24 次/天 ≈ **0.42 MB/天，约 155 MB/年**
- `config.RAW_RETENTION_DAYS = None` 表示永久保留；想轮转就填天数（如 `30`），每次抓取时自动清理过期文件
- 留档里含目前未解析的字段（`style_type`、`display_num`、`head_zone`、`head_zones` 等），将来要用随时回溯，不用重新采集
- 同一秒内重复抓取会自动加 `-2`/`-3` 后缀，不覆盖已有文件

## 数据模型

```
snapshot     一次抓取（fetched_at, item_count）
hot_topic    去重后的热榜话题（question_id 为主键）
observation  某话题在某次快照里的那条记录（排名/热度/回答数/关注数/是否新上榜）
```

峰值、当前热度、增量、变化率**全部查询时计算，不落表**，避免冗余数据对不上。

`observation.attached_info` 原样保留（知乎的 base64 protobuf），哪天想逆向出精确热度不用补历史数据。

## 接口实测记录（2026-09-13）

- 每次返回 **29 条**，`paging.is_end=true`，无分页游标，一次即全量
- `trend` 恒为 0、`comment_count` 恒为 0 → 不可用，涨跌一律自己算
- `detail_text` 是 `"474 万热度"` 这种中文串，**精度只到万**，小时级增量可能只是四舍五入噪声；排名是整数，比热度变化率可信
- 稳定身份是 `target.id`；顶层 `id` 是 `{排名}_{服务器时间戳}`，每次刷新都变
- **`target.url` 是 API 地址**（`https://api.zhihu.com/questions/{id}`），浏览器打开会看到 `{"error":{"message":"请求参数异常…","code":10003}}`。入库时统一换成 `https://www.zhihu.com/question/{id}`；老数据由 `init_db()` 自动回填
- 老问题会反复上榜（2019 年的问题今天仍在榜），所以按 id 去重而不是按标题
- 知乎原生 `bound_topic_ids` 太碎（29 个话题对应 113 个标签，几乎一对一）且匿名拿不到标签名，**不做聚合维度**
- 规模：29 × 24 = 696 行/天 ≈ 25 万行/年，SQLite 无压力
